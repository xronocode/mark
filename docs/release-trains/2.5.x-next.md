### FIX-002

Measure and repair the reported file-open latency regression.

- **Reported:** owner, 2026-10-20. A file selected in the sidebar took about five seconds to appear in a tab; the comparison with 2.5.0 is perceptual and has no timing capture yet.
- **Expected:** an ordinary local file click opens without a multi-second idle delay and without regressing external/cold-open behavior.
- **Instrumentation (in `a2d77872`, 2026-10-20; strengthened after the trace):** a four-phase trace with stable markers — `[sidebar][open-file][BLOCK_OPEN_FILE_CLICK dispatch_ms=…]` (dispatch_ms = `performance.now()` minus the DOM event timeStamp, exposing main-thread congestion between the physical click and the handler), `[boot][pending_opens][BLOCK_OPEN_FILE_ARRIVAL since_click_ms]`, `[editor][open-file][BLOCK_OPEN_TAB_CREATED since_arrival_ms]`, `[editor][open-file][BLOCK_OPEN_FIRST_PAINT since_arrival_ms]` (treeFile.vue, bootstrap-ipc.js, store/editor.js, editor.vue handleFileChange — the actual render path; the parallel file-loaded delivery skips as a duplicate).
- **Measured renderer legs (chromium/Playwright on the `a2d77872` build):** event arrival → tab state ≈ 9–10 ms; arrival → first paint ≈ 12 ms for a small document; ≈ 840 ms to the tab state for a ~600 KB document (opened-baseline snapshot + document state build).
- **Real-app trace (2026-10-20, `tauri dev` build of the wave source, WKWebView + Rust, dev-diag console capture):** ordinary small file — click → arrival **16 ms** (the full `mt::open-file` invoke → Rust read → emit → WKWebView delivery pipe), arrival → tab **2–9 ms**, arrival → first paint **32 ms**. The IPC/backend/event-delivery pipe is millisecond-scale and is **not** the reported delay.
- **Reproduction of the ~5 s (same real-app trace, 1.7 MB / 9000-section document):** click → arrival **66 ms**, arrival → tab **2 ms**, arrival → first paint **4863 ms** (up to ~29 s at cold boot under memory pressure). Phase profile: markdown parse ≈ 26 ms, snabbdom render ≈ 0.9–1.2 s, and the remaining ~5–7 s is the main thread blocked by WebKit style/layout of the freshly created ≈30k-node DOM (the next macrotask — muya's deferred `dispatchChange` — stalled 6.6–7.3 s behind it).
- **Attribution:** the reported multi-second open latency is the **initial render + layout cost of a large document in the renderer**, not an IPC, backend or tab-creation regression. A small file paints in ~50 ms end to end on the same build and machine — the reported expectation («an ordinary local file opens without a multi-second delay») holds on the current build; the ~5 s reproduces only on a megabyte-scale document.
- **Repair decision:** a real repair means chunked/virtualized initial rendering of huge documents — a structural change that needs its own GRACE change spec (the FIX-* lane does not retrofit it). The durable four-phase trace stays in place so the owner's exact file reproduces through the same markers; the physical-click dispatch leg is covered by the new `dispatch_ms` field.
- **Presented for owner acceptance (2026-10-20):** the attribution and the repair decision were handed to the owner in [mark-fix002-attribution-and-decision-2026-10-20.md](../../../Downloads/mark-fix002-attribution-and-decision-2026-10-20.md) (opened in Mark). Two options: (A) open the structural change spec now; (B) accept the attribution and keep large-document rendering as a known limitation with a backlog improvement. Recommendation recorded: option B now, spec (A) as planned follow-up work — unless megabyte documents are a daily scenario.
- **Proposed scope for the follow-up spec (drafted, awaits the owner's decision to open it):** first-paint window rendering for large documents — render the initial viewport's blocks synchronously, materialize the remaining document progressively (background chunks and/or scroll-driven), preserving scroll position and cursor restore, history/undo correctness, exports, search, the outline and the diff baseline; acceptance gates: first paint of a 1.7 MB document within a few hundred milliseconds, no content-loss path (corner matrix), unchanged budgets for ordinary files, four-corner review.
- **Automated evidence:** `tests/e2e/open-file-timing.spec.ts` (chromium) pins marker presence and the renderer-leg budgets; V-M-025 carries the command and the four markers.
- **Train/state:** `2.5.x-next` / attributed and presented for owner acceptance. Implementation of the structural repair is blocked on the owner's decision to open the change spec — that decision is the single remaining input.

### FIX-009

Separate cold-start session restoration from recovery of tabs closed during the current run.

- **Reported:** owner, 2026-10-20. Steps: close the open tabs, then click “Last session” on the welcome screen. Nothing happens.
- **Root cause:** `recent/index.vue` captures `sessionPaths` when the welcome screen mounts. Independently, `START_SESSION_AUTOSAVE` correctly writes the current empty tab list to `lastSessionTabs` 400 ms after the last tab closes. The row keeps displaying its earlier local list, while `RESTORE_SESSION()` rereads the now-empty preference and has nothing to open.
- **Owner decision, 2026-10-20 — cold start:** add a “Restore last session on launch” preference, enabled by default. With it enabled, a cold launch restores the persisted tabs, active tab and workspace roots automatically. With it disabled, the welcome screen may expose “Last session” as an explicit cold-start action. The action must reflect a real restorable prior-session snapshot and must never silently no-op.
- **Owner decision, 2026-10-20 — current run:** once the window is running, closing tabs changes the live session, including legitimately reaching zero tabs. Recovery is provided by a separate session-scoped “Recently closed” history, not by “Last session”. A compact history button with a count appears beside the tab strip's `+`; its popover can reopen one entry or “Reopen all N”. When the final tab closes, the welcome screen exposes the same current-run recovery prominently. `Shift+Cmd+T` reopens entries from newest to oldest.
- **History semantics:** retain the restorable saved-file tabs closed since the current window started; consume an entry when it is restored or opened independently; deduplicate a repeatedly closed pathname to its newest entry; preserve enough root, ordering and active-tab metadata for deterministic “Reopen all”; bound the list; clear it on the next cold launch. Unsaved untitled drafts remain outside this recovery path until a durable draft mechanism exists.
- **Workspace boundary:** removing a workspace root is not a closed-tab event. Multi-source workspace removal needs its own immediate Undo affordance and must not be mixed into the recently closed document list.
- **Design reference:** [dark-theme recently closed tabs mockup](../../work/recently-closed-tabs-mockup.png).
- **Verification gap:** current C-69 coverage verifies a cold restore and closing one tab before relaunch, but not the startup preference branches, closing tabs down to zero after the autosave debounce, individual/all current-run recovery, repeated close/reopen cycles, missing files or the separation from workspace-root removal.
- **Acceptance target:** default cold launch restores the prior persisted session automatically; disabling that preference leaves a working explicit “Last session” action. During the current run, the closed-tab button and empty-screen action recover exactly what they advertise, including “Reopen all”, and no stale action can silently no-op.
- **Train/state:** `2.5.x-next` / product behavior approved for backlog refinement only. The expanded behavior requires an approved GRACE change spec and plan before implementation; automated regression, native verification and owner acceptance remain pending.
